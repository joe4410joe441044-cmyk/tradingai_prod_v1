### 3.1 Reading conventions and physical limits

`E` = `backend/runtime/cycle_evidence_store.py` via `knowledge_history_sources.CycleEvidenceSource`; `T` = `backend/runtime/trading_trace_reader.py` via `TradingTraceSource`; `Q` = `knowledge_history_query.py` and `knowledge_history_models.py`. These are the **only two registered Shared Query sources**. `completed_trade_evidence` and `parameter_revision_evidence` in `cycle_evidence_links.py` are pure projections, not registered store readers.

E verifies envelopes and isolates malformed/truncated/integrity-failed records. Its source adapter caps yielded scan records at 50,000, but `iter_records` uses unrestricted `readline`, ignores blank lines, and cursor resumption walks/validates the preceding prefix before the adapter starts counting. Therefore its advertised bounded flag is not a strict byte/time/physical-line bound. T has byte/line/time budgets (default 8 MiB and 200,000 lines, max page 200), snapshot/cursor guards and partial scan reporting. Q max returned limit is 200, with provenance, availability, corruption, unsupported-filter and pagination metadata. Pagination is not proof of complete coverage. Continuous use requires verified physical bounds for **every** adapter; do not fix them in this task.

Q freshness defaults to a named 3,600-second policy using source observation metadata (file mtime); snapshot freshness provisionally uses 30 seconds and one-second future tolerance. Preserve these differing policy identities. File mtime does not certify event recency or completeness. Historical events may be old and valid; freshness concerns source observation and expected production, not the age of every baseline record. Size-based E revisions are not immutable content versions; no full snapshot isolation is guaranteed across pages.

## 4. Historical baseline contract (proposed)

All numbers below are V1 reviewable engineering defaults, not calibrated trading thresholds. No values are enabled by this audit. Every metric definition carries metric_version, policy_version, source schema, units, numerator, denominator and eligibility predicate. Store the source query and completeness proof with each observation. Deduplicate the same canonical source record across E/T; choose T for decision/evaluation populations, E for Phase A-specific details. Do not count two projections as two outcomes. Identity/revision joins must be explicit; phase-a keys cannot fill missing authority links.

Common grouping G: deployment scope, PAPER/LIVE, symbol (except symbol-distribution metric), effective Parameter revision, strategy/feature contract and controlSource when captured. Unknown revision is its own unavailable stratum, never merged with current revision. No cross-revision or cross-mode baseline fallback. An explicitly observed regime label can be an additional group; otherwise regime is UNKNOWN and no causal attribution is made.

Windows use UTC half-open intervals and a deterministic evaluation cutoff. Profile F: current last 1 hour, baseline preceding 7 days excluding current; cutoff is the latest completed minute minus 120 seconds. Minimum denominators 100 current/500 baseline. Profile S: current last 24 hours, baseline preceding 30 days; minimum 30/100. Profile H: current last 15 minutes, baseline preceding 24 hours, minimum 10/100 scheduled observations. Profile R: current revision epoch vs up to 10 preceding known revision epochs (maximum 90 days); minimum two timestamped revisions for a period, five complete periods for comparison. Historical-only comparisons stay labelled historical if sources are not live/fresh.

Freshness FQ: preserve Q freshness policy/state AND prove the requested current interval is fully covered; event inactivity does not imply capture failure without an expected-production signal. FS: same coverage rule plus exit-time authority; no stale-file-to-empty-trades inference. FH: observed sample age <=120 seconds with valid source time; generated read timestamps alone cannot prove producer freshness. FR: archive read succeeds and revision/times validate; old unchanged revision is not stale solely due to age. Snapshot observations retain their existing 30-second policy; monitoring must not relabel stale source inputs fresh.

Universal insufficient behavior I: retain null metric (never zero), counts, missing requirements, INSUFFICIENT_DATA for complete but too-small cohorts, UNKNOWN for unavailable/unsupported authority, STALE for failed freshness, PARTIAL for incomplete scans. No statistical drift alert from invalid cohorts. Universal restart behavior D: reconstruct only from canonical retained records using validated source revision/cursors; if coverage cannot be proved, remain incomplete and warm up. H metrics require persisted monitoring observations from Phase 2; memory-only restart loses their baseline. R requires exact archived revisions; never reconstruct dates from revision numbers.

Precedence for metric state: unavailable/invalid authority => UNKNOWN; otherwise stale required authority => STALE; otherwise incomplete coverage => PARTIAL; otherwise insufficient eligible samples => INSUFFICIENT_DATA; otherwise apply NONE/INFO/WARNING/CRITICAL policy (NONE maps to NORMAL). Do not classify a missing identity as a confirmed identity-chain break.

Baseline populations are stratified at Parameter revision changes. Revision change itself produces INFO and a new warm-up epoch, never evidence of trading failure. Expected regime change requires an explicit contemporaneous authoritative regime label with provenance and known policy; an LLM narrative or price movement cannot certify it. Such a change may explain statistical drift but never suppress corruption or safety contradictions. Correlation is not cause.

## 6. Severity policy V1 (proposed, deterministic)

Eligible proportion differences use absolute percentage-point delta d and two-proportion standard error s = sqrt(p_current*(1-p_current)/n_current + p_baseline*(1-p_baseline)/n_baseline). INFO when d>=0.05; WARNING candidate when d>=0.10 and (s=0 or d>=3*s). Distribution total variation = 0.5*sum(abs(p_current-p_baseline)); INFO >=0.10, WARNING candidate >=0.20. Continuous comparable measurements use median displacement / max(baseline MAD, declared positive unit-specific floor); INFO >=3, WARNING candidate >=6. A metric lacking a declared floor/units has no numeric severity rule and remains unsupported. These are engineering screens, not significance/p-value claims; require minimum samples and full coverage from section 4.

| Severity | Deterministic trigger | Persistence / safeguards |
|---|---|---|
| NONE / NORMAL | Valid comparable measurement below thresholds and no independent anomaly | A successful query alone cannot resolve an alert. |
| INFO | Minor deviation above INFO threshold; newly observed authoritative Parameter revision; complete but insufficient non-critical history | Revision event once per revision identity. INSUFFICIENT_DATA state remains visible with INFO severity where applicable. |
| WARNING | Candidate/signal/rejection distribution meets WARNING rule in 3 consecutive comparable observations with advancing cutoff; important source stale in 3 runs spanning >=120s; independently expected evidence gaps in 3 such runs | Identical retry observation IDs do not advance persistence. One missing optional field or OFF capture does not qualify. |
| CRITICAL | Proven execution/position or runtime/exchange contradiction; explicit link mismatch for identities that should match; fresh safety-authority inconsistency; same corruption identity in 3 distinct scans spanning >=120s | Contradictions require same mode/account/order/position and aligned event version or documented ordering, not sequential snapshots from different moments. Current sources may be insufficient to establish these facts; then UNKNOWN/PARTIAL. |

Examples: realOrderAllowed=true while the same authoritative decision/version says governance execution disabled is a safety inconsistency; an order submitted followed by no fill evidence is not a contradiction. Corruption persistence tracks source record identity/digest and revision; repeated scanning of the same bad record raises count of observations, not number of corrupt records. Missing critical data is WARNING with missing/stale state unless independent proof supports CRITICAL. Statistical drift alone never escalates automatically to CRITICAL.

Confidence does not cancel a proven safety finding; evidence requirements decide whether the finding exists. Valid fresh NORMAL measurements in 3 distinct comparable observations spanning >=120s resolve a statistical episode. Integrity episodes need the specific contradiction/corruption resolved by authoritative replacement/reconciliation evidence read-only; disappearance due to retention or scan failure is not resolution. UNKNOWN/STALE/PARTIAL/INSUFFICIENT_DATA never auto-resolve an existing incident.

Every severity is advisory metadata. There is no output capability for Parameter/MM/Governance mutation, Bot START/STOP, ARM/DISARM, execution/cancel/close, trading decisions or automatic remediation.

## 7. Restart-safe deduplication and cooldown (design only)

Anomaly fingerprint = hash(schema family, policy/metric version, deployment/account scope if authoritative, PAPER/LIVE, group dimensions, category, reason family, effective revision, and offending identity for integrity findings). Exclude timestamps, measured magnitude, severity, provider text and localized labels. This keeps continuing drift in one episode and permits escalation. Source revision is stored on each observation, not universally part of the fingerprint; appending a trace must not create a new alert. Parameter/metric policy changes intentionally create new comparison epochs.

Future records must include: alert_id, anomaly_fingerprint, episode_number, first_seen, last_seen, occurrence_count, last_observation_id, last_notified, cooldown_until, highest_severity, current_severity, escalation_version, status OPEN/ACKNOWLEDGED/RESOLVED, resolution observation/reason/time, acknowledgement actor/time/note, source revisions, schema_version and policy_version. Times are UTC; cooldown decisions use persisted UTC deadlines with backwards-clock detection. Clock regression suspends delivery eligibility and reports UNKNOWN health.

Apply unique observation IDs transactionally: retries are no-ops; occurrence_count increments only for a new accepted observation in that episode. Persist observation reference, state transition and eligibility/outbox record atomically. `last_notified` means confirmed delivery, never evaluation or formatting; Phase 4 does not set it because no delivery exists. An internal `last_eligible_at` and unique outbox key prevent repeated enqueueing meanwhile.

Proposed cooldown: WARNING 60 minutes, CRITICAL 15 minutes. INFO is visible but never externally eligible. Same-severity repeats within cooldown suppressed. Escalation WARNING->CRITICAL bypasses cooldown once per escalation_version; retries do not. Acknowledgement suppresses same/lower-severity repeat eligibility for 24 hours (actor and expiry explicit), but not escalation. ACK is not resolution. Recurrence after resolution creates a new episode; do not reopen and overwrite previous history. Source rotation invalidates cursor and starts bounded recovery, not a new anomaly by itself.

| Classification | Option | Decision |
|---|---|---|
| REUSE_EXISTING | Canonical E/T/Stage 13/Parameter authorities and sanitizers | Reuse read-only; never duplicate raw knowledge/evidence into a new truth store. |
| EXTEND_EXISTING | Versioned monitor-owned tables in existing Supervisor SQLite infrastructure | Preferred durable operational-state option after explicit migration/retention/locking review. Existing event schema alone is insufficient; add state, observation-id dedup, samples, lease and later outbox with bounded indexes/quotas. |
| NEW_STORE_REQUIRED | Dedicated monitoring SQLite if shared DB contention/retention ownership cannot be safely isolated | Conditional alternative, not a second simultaneous state store. Only derived operational state/references, no duplicated knowledge corpus. Select one backend before Phase 2 approval. |
| REJECT_DUPLICATE | New JSONL evidence corpus, separate Advisor/Supervisor historical truth, dual monitor stores | Reject; use Shared Query and one monitoring state authority. |
| UNSAFE | Memory-only cooldown, provider/conversation text as alert truth, writing Bot/trace/Parameter stores, reusing router constructor for reads | Cannot meet restart/authority requirements. |

Recommendation is EXTEND_EXISTING with separate tables; no schema is added here. Enforce transaction rollback on disk-full/busy/corruption; suppress new notification eligibility until durable state succeeds, expose degraded monitor health, never propagate into Bot runtime. Define bounded retention: at most 10,000 open episodes, 100,000 observation dedup keys and 100,000 samples initially, with explicit retention/compaction policy before activation. Do not evict unresolved episodes or dedup keys still needed by replay windows. When quotas cannot preserve those invariants, stop ingestion and report capacity rather than silently dropping state. TTL must exceed maximum replay horizon/cooldown; source-derived data cannot be deleted by monitor retention.

## 8. Scheduler design only

Recommended new flag: `AI_SUPERVISOR_CONTINUOUS_MONITORING_ENABLED`, default OFF and independent of provider and existing consumer flags. Flag OFF means no runner, lease, query, new monitoring store initialization or health timer. A future application composition must lazily construct monitoring resources only when explicitly enabled; do not reuse today's side-effecting Supervisor router construction as that factory. No flag is added in this task.

| Concern | Proposed contract |
|---|---|
| Interval/startup | 60-second interval, initial delay 30 seconds after successful application composition. No missed-run catch-up queue. Evaluation cutoff/windows remain deterministic. |
| One active runner | Deployment-scoped OS advisory exclusive lock plus DB fencing generation. One configured monitor host/instance; replicas OFF. Never use process-local lock as multi-worker guarantee. Cross-host enablement is rejected until a distributed lease/fencing design is approved. |
| Overlap prevention | Single run mutex shared by scheduled and manual paths; busy manual one-shot returns BUSY, scheduled tick records skipped_busy. Hold lock until underlying I/O actually terminates, not just until await timeout. |
| Time budget | 10s total run; 2s per source; 5s maximum graceful cancellation wait. Cooperative cancellation checked during scanning; blocked I/O cannot leave an uncancelled worker racing a new run. |
| Physical/query budget | At most 4 shared pages/run, 200 returned items/page, 800 total items, 8 MiB total scan bytes and 50,000 physical lines across all adapters; max line 256 KiB. Every scan, including skipped prefixes/blank lines, consumes budget. Excess is PARTIAL, never normal. |
| Historical recovery | Checkpoint per bounded scan and exact query/window/policy. Validate revisions/digests on resume; append/rotation handling must preserve coverage proof. No unbounded rewind. Baseline remains warming/partial until complete. Never merge checkpoints for different rolling windows into a claimed complete cohort. |
| Event-loop isolation | Certified bounded readers run in an isolated observation I/O executor with cooperative deadlines; if cancellation cannot terminate work, health becomes stuck and subsequent runs are suppressed until exit. Do not claim `asyncio` cancellation terminates a blocking thread. No network/exchange/provider clients in worker. |
| Backpressure | One active job and zero queued ticks; skip ticks, no burst after downtime. If state/outbox quotas are reached, suspend eligibility and publish degraded health. |
| Failure isolation | Source failure produces source UNKNOWN/PARTIAL; other independent metrics may continue. Monitor failure cannot throw through Bot lifecycle, readiness gates, or execution decisions. No retry storm. |
| Shutdown | Stop accepting ticks/manual requests, cancel current scan, await bounded completion, roll back incomplete transaction; release fence/lock only when no writer remains. On forced exit transaction recovery applies at next start. |
| Restart | Acquire exclusive ownership, validate schema, recover committed checkpoints/episodes/cooldowns; abandoned incomplete run is marked interrupted on authorized future state write. No alert delivery replay before eligibility reconciliation. |
| Health/read model | enabled, running, owner/fence, last_started/completed/success, last_error_code, last_duration, next_due, skipped_busy, budget_exhausted, source states, checkpoint age, warm-up and store/outbox capacity. No mutation through health GET. |
| Manual one-shot | Phase 1 injected inputs/pure calculation, no application import or persistence. After Phase 2, explicitly selected persisted one-shot shares lock/budgets/state semantics and remains independent of recurring flag. No implicit notifications. |

The existing E physical-budget gap, unbounded archive/Stage 13 readers, non-atomic runtime reads, and absent historical coverage proofs are activation gates. They do not block completing this documentation audit. Any future adapter hardening is a separately approved prerequisite task, not a rerun of Work-I② or permission to change it here. An optional unready source can remain disabled with explicit UNKNOWN metrics; a source actually used by a runner must pass every physical bound and authority gate.

## 9. Notification design

1. **Anomaly creation:** deterministic observation and episode update, independent of any transport or LLM.
2. **Eligibility:** require committed state, WARNING/CRITICAL, valid evidence for that category, cooldown/ack/suppression checks, unique (alert_id, episode, escalation_version, notice_kind, cooldown_bucket) key. State-store failure means ineligible, not an in-memory send.
3. **Formatting:** deterministic sanitized summary with alert ID, metric/unit, category/severity, sample sizes, windows, current/baseline values, reason codes, provenance, freshness policy and uncertainty. Format after eligibility; formatting failure does not mark delivered.
4. **Delivery:** separate future adapter with approved destination/channel/credentials, idempotency and explicit human authorization for external transmission. Phase 4 creates only an internal durable outbox. No transport is implemented/connected in Phases 1–5.
5. **Acknowledgement:** authenticated user metadata action on monitoring state; idempotent, actor/time retained, no changes to trading controls or causal conclusion.
6. **Resolution:** evidence-based state transition from section 6; a human may annotate but cannot make stale/missing evidence become NORMAL. Recovery notice eligible once only for an episode whose earlier external delivery was confirmed; internal-only episodes get internal resolution records.

Suppress INFO, disabled monitor, duplicate observation/outbox key, active same-severity cooldown, applicable ACK and expired/superseded notice. Do not suppress CRITICAL escalation because an old WARNING was acknowledged. Before future delivery, revalidate episode state/severity/expiry and avoid sending stale queued escalations after recovery. Timeout/unknown delivery outcome must not update last_notified as success; retain uncertain attempt and reconcile with an idempotency key before retry. Exactly-once external delivery cannot be promised without transport support.

Stale/partial disclaimer is mandatory whenever applicable: EN “Evidence is stale or incomplete; this alert does not establish current trading state.” JA “証拠が古い、または不完全です。このアラートは現在の取引状態を確定するものではありません。” Emit metric/severity codes and UTC times unchanged in both languages, with optional localized display times. Evidence links are allowlisted application routes or canonical IDs with access control, never raw filesystem paths, credentials or arbitrary provider-generated URLs. Translation and Advisor prose cannot raise severity or change eligibility. External delivery approval is destination-, content- and environment-specific and is not implied by design approval or controlled Production read acceptance.

## 10. Advisor explanation of Supervisor alerts

Future flow: Supervisor persists an alert ID and bounded decision metadata; user asks Advisor about that ID; an authenticated read-only alert lookup returns the metric/policy/window/query references and provenance; Advisor queries the **same Shared Query facade** using that exact scope, source identifiers and freshness policy. Advisor explains what changed, supporting evidence, what cause is actually established, alternative explanations and uncertainty. A lookup failure returns unavailable; it does not search arbitrary unrelated recent records and claim a match.

The alert state is an operational index, not a private knowledge store. Store source identifiers/digests/query parameters, aggregates and reason codes, not a duplicate raw evidence corpus. Both consumers must receive identical source provenance/freshness authority for the same query, policy and evaluation-as-of time. The existing Supervisor/Advisor request plans (6/8 default items) are not suitable for replaying a population baseline; a future bounded alert-specific query plan must expose partial reconstruction explicitly. No new separate evidence truth or direct bypass reader in Advisor.

At explanation time sources may have appended, rotated or been removed. Compare returned revisions/digests with those recorded at alert creation. If different, label “original observation” versus “current re-query”; do not pretend the newer answer reproduces the historical calculation. Historical query metadata is retained as decision evidence, not re-labelled current freshness. If exact evidence no longer exists, disclose that exact reproduction is unavailable. Any later Stage 13/archive adapter belongs in Shared Query for both consumers.

No Supervisor private prompt, provider, conversation history or LLM output is required to resolve/explain an alert. Advisor cannot acknowledge/resolve implicitly, mutate settings, or acquire trading authority. Acknowledgement is a separate explicit authenticated user action. Tests must prove identical source/policy provenance, missing-ID handling, changed-source disclosure, injection resistance, redaction and no command access.
